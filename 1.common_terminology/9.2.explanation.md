### Главная идея документа 9.2: Зачем нужен Context Compiler?

#### Проблема «сырых» контекстов (Naive Dump):

Большинство современных Coding Agents (автономных программистов) действуют «в лоб»: они собирают все файлы репозитория, склеивают их в один огромный текст на 50 000 – 100 000 токенов и отправляют в LLM[3].

Чем это плохо[3]:

1. **Lost in the Middle (документ 8.5):** Модели отлично читают начало и конец промпта, но «слепнут» в середине огромных контекстов[4][5].
2. **Огромные расходы и задержки (Latency &amp; Cost):** Передача десятков тысяч ненужных токенов при каждом вызове API увеличивает стоимость и время ожидания ответа[3][6].
3. **Шум в контексте:** Реальная логика функции размывается среди сотен строк реализации соседних нерелевантных модулей[3].

#### Решение: Подход компилятора (Context Compiler)

Вместо того чтобы надеяться на гигантское контекстное окно LLM, нужно скомпилировать минимально необходимый контекст **ДО** того, как промпт уйдет в API[3].

Мы оставляем **полный код** только для редактируемого файла, **сигнатуры и интерфейсы** — для зависимостей, а все остальное — **удаляем**


### Data Pipeline Architecture (Архитектура пайплайна данных)

Обработка кода перед отправкой в LLM проходит через **3 фазы (3 Passes)** за один вызов `compile()`[7]:

```
[ Целевой файл (Target) ]
         │
         ▼
[ Pass 1: Symbol Resolution ] ──► Построение графа зависимостей (Reachability Graph)
         │
         ▼
[ Pass 2: Interface Extraction ] ──► Скелетизация (AST Body-Stripping)
         │
         ▼
[ Pass 3: Context Assembly ] ──► Сборка 3-уровневого промпта (3-Tier Output)

```

#### Фаза 1: Symbol Resolution (Анализ достижимости)

* **Задач:** Понять, какие файлы проекта действительно связаны с файлом, который редактирует разработчик[7].
* **Как работает:** Модуль `SymbolResolver` анализирует `import` и имена вызываемых функций (call sites) от целевого файла наружу[2][7].
* **Параметр** **max\_hops** **:**
  * `max_hops = 1`: Находит только прямые импорты и вызовы целевого файла[8].
  * `max_hops = 2` (дефолт): Находит прямые зависимости + зависимости следующего уровня[8].

#### Фаза 2: Interface Extraction (Скелетизация кода)

* **Задача:** Уменьшить размер найденных файлов-зависимостей без потери их смысла для LLM[7].
* **Как работает:** `CodeSkeletonizer` использует встроенный в Python модуль `ast` (`ast.NodeTransformer`)[7][9]. Он обходит дерево кода и **вырезает тела функций и методов** (заменяя их на `...` или `pass`), но **строго сохраняет**:
  * Сигнатуры функций и методов (имена, аргументы)[7].
  * Декораторы[7].
  * Аннотации типов (Type Hints)[7].
  * Докстринги (Docstrings)[7].

#### Фаза 3: Context Assembly (Трехуровневая сборка контекста)

Каждый файл репозитория распределяется по трем уровням (Tiers)[7][10]:

| Уровень (Tier)         | Какой код попадает                        | В каком виде передается в LLM                          |
| ---------------------- | ----------------------------------------- | ------------------------------------------------------ |
| **Tier 1 (Target)**    | Целевой файл, который мы редактируем      | **Полный исходный код**[10]                          |
| **Tier 2 (Reachable)** | Файлы-зависимости (в пределах `max_hops`) | **Скелетированный код** (только интерфейсы)[7][10] |
| **Tier 3 (Excluded)**  | Несвязанные файлы репозитория             | **Исключаются полностью** (0 токенов)[7][10]       |

#### Результат пайплайна:

На реальных тестах этот пайплайн снижает объем токенов на **69% – 74%** за 50–70 миллисекунд работы на CPU (без сторонних тяжелых библиотек)[6]

### 1\. Разбор фразы из 9.2

&gt; *"it falls back to checking a repo-wide symbol table, expanding outward breadth-first up to a set hop limit."*

Перевод и смысл по частям:

* **falls back to...** — *(переходит к резервному варианту)*. Если статическому анализатору не удалось отследить точный `import` (например, если используется `from module import *` или имя передано динамически).
* **repo-wide symbol table** — *(глобальная таблица символов всего репозитория)*. Это словарь всех функций, классов и методов, объявленных во всех файлах вашего проекта.
* **expanding outward breadth-first** — *(расширяя область поиска в ширину, BFS)*. Поиск идет от целевого файла по графу вызовов слоями: сначала проверяются прямые связи (шаг 1), затем связи этих связей (шаг 2) и так далее.
* **up to a set hop limit** — *(вплоть до установленного лимита шагов/переходов)*. Ограничение глубины поиска (параметр `max_hops`, например `max_hops=2`), чтобы не затянуть в контекст весь репозиторий.

**Простыми словами:** *«Если компилятор не может по* *import* *точно определить, откуда взялся класс или функция, он активирует запасной план: ищет это имя в общей базе символов всего проекта и пошагово продвигается в ширину по связям не дальше заданного количества шагов (например, не дальше 2 кликов от редактируемого файла).»*

### 2\. Как обернуть `ContextCompiler` в инструмент (`@tool`) для AI-Агента

Чтобы AI-агент (например, на LangChain / LangGraph или CrewAI) самостоятельно вызывал `ContextCompiler` перед внесением изменений в код, мы оборачиваем компилятор в инструмент с подробным описанием (docstring). Описание критически важно: именно по нему LLM понимает, **когда** и **зачем** вызывать инструмент.

Вот готовый рабочий код:

```
from pathlib import Path
from langchain_core.tools import tool
from pydantic import BaseModel, Field

# Импортируем сам ContextCompiler из репозитория
from compiler import ContextCompiler

class CompileContextInput(BaseModel):
    target_file: str = Field(
        description="Относительный или абсолютный путь к файлу, который агент собирается редактировать или анализировать."
    )
    max_hops: int = Field(
        default=2,
        description="Глубина графа зависимостей (1 = только прямые импорты, 2 = импорты импортов). По умолчанию 2.",
    )

@tool("get_compiled_code_context", args_schema=CompileContextInput)
def get_compiled_code_context(target_file: str, max_hops: int = 2) -&gt; str:
    """Используй этот инструмент ПЕРЕД редактированием или написанием кода.
    Он анализирует AST-дерево репозитория, находит только связанные с target_file модули,
    вырезает тела ненужных функций (скелетизация) и возвращает токен-оптимизированный контекст.
    """
    # Определяем корень репозитория (можно задать явно или брать текущую директорию)
    repo_root = Path(".").resolve()
    target_path = Path(target_file).resolve()

    if not target_path.exists():
        return f"Ошибка: Файл {target_file} не найден в репозитории."

    try:
        # Инициализируем компилятор
        compiler = ContextCompiler(repo_root=repo_root)

        # Компилируем 3-уровневый контекст (Tier 1: полный код, Tier 2: скелеты, Tier 3: исключены)
        compiled_result = compiler.compile(
            target_file=target_path, max_hops=max_hops
        )

        # Возвращаем скомпилированную строку промпта напрямую в LLM
        return compiled_result.prompt_text

    except Exception as e:
        return f"Ошибка при компиляции контекста: {str(e)}"

```

#### Как это работает в цикле Агента:

1. **Пользователь пишет агенту:** *"Исправь баг в файле app/views.py"*.
2. **Агент (LLM) видит доступный инструмент** `get_compiled_code_context`.
3. **Агент вызывает инструмент:** `get_compiled_code_context(target_file="app/views.py")`.
4. **Инструмент за 2 миллисекунды:**
  * Оставляет `app/views.py` **полностью** (Tier 1).
  * Оставляет для зависимостей (`models.py`, `services.py`) **только сигнатуры и докстринги** (Tier 2).
  * Выбрасывает нерелевантные файлы (Tier 3).
5. **Агент получает компактный промпт** (вместо 100k токенов сырого кода — всего 300–500 токенов) и генерирует точный код без потери контекста.

### Терминология: "Сигнатура", "Докстринг" и "Интерфейс взаимодействия"

Представьте функцию в Python:

```
def charge(self, amount: float, currency: str = 'USD') -&gt; bool:
    """Занимается списанием средств с карты пользователя в указанной валюте."""
    # --- НАЧАЛО ТЕЛА ФУНКЦИИ ---
    data = {"amount": amount, "currency": currency}
    response = requests.post("https://api.stripe.com/v1/charges", json=data)
    if response.status_code == 200:
        return True
    return False
    # --- КОНЕЦ ТЕЛА ФУНКЦИИ ---

```

* **Сигнатура (Signature):** Это первая строка объявления функции без ее внутренней реализации.

&gt; `def charge(self, amount: float, currency: str = 'USD') -&gt; bool:` Она говорит: *«У функции имя* *charge* *, она принимает* *amount* *и* *currency* *, а возвращает* *bool* *»*.

* **Докстринг (Docstring):** Это строка документации под сигнатурой (в тройных кавычках `"""..."""`).

&gt; `"""Занимается списанием средств с карты пользователя в указанной валюте."""` Она объясняет словами, *что* делает эта функция.

* **Что значит "Только интерфейс взаимодействия"?** Скелетизатор (Skeletonizer) удаляет из кода все **тело функции** (запросы к API, циклы, условия) и оставляет только сигнатуру, докстринг и `...`:

```
def charge(self, amount: float, currency: str = 'USD') -&gt; bool:
    """Занимается списанием средств с карты пользователя в указанной валюте."""
    ...

```

Это и есть **интерфейс взаимодействия (контракт)**. Для LLM (и для разработчика) этого достаточно, чтобы понять, **как правильно вызвать эту функцию** из другого файла, не тратя токены на чтение 100 строк её внутреннего кода.

### 3\. Где "Глобальная таблица символов всего репозитория"?

Такая таблица **не хранится в виде отдельного файла на диске**.

**Глобальная таблица символов (Symbol Table)** — это виртуальный словарь (Dictionary в Python), который модуль `symbol_resolver.py` **собирает в оперативной памяти** во время запуска.

Как это работает в реальных проектах:

1. `symbol_resolver.py` открывает все `.py` файлы проекта один за другим.
2. С помощью встроенного модуля `ast` он сканирует файлы и формирует в памяти словарь вида:

```
{
    "PaymentProcessor": [Path("app/models.py")],
    "charge": [Path("app/services.py")],
    "save": [Path("app/models.py"), Path("app/models_order.py")]  # Конфликт имен!
}

```

1. Когда компилятор видит, что `views.py` вызывает функцию `save()`, но не понимает точный импорт, он берет этот словарь из памяти и проверяет: *"Так,* *save* *объявлен в* *models.py* *и* *models\_order.py* *. Возьму оба файла в Tier 2 на всякий случай!"*

### 4\. Разбор вывода DEMO 4 и DEMO 5

#### DEMO 4: Три главных ограничений статического анализа (Edge Cases)

Статический анализ кода читает текст файла, не заменяя его реальным исполнением в Python. Поэтому скрипт честно показывает 3 случая, где он пасует:

1. **Signals / Event decorators (** **@receiver** **):** В `services.py` есть функция `notify_on_save()`, перехватывающая события. Но в `views.py` нет прямого импорта или вызова этой функции. В коде нет прямой видимой связи, поэтому анализатор не включает её в зависимости, а выдает как предупреждение (`hint`).
2. **Dynamic dispatch (** **getattr()** **,** **importlib** **):** В `views.py` модуль загружается по имени через строку `importlib.import_module(f"app.handlers.{name}")`. Так как имя `name` определяется во время работы программы, статический анализ не гадает и исключает файлы обработчиков в Tier 3\. *(Философия библиотеки: лучше не додать контекста, чем дать ложный)*.
3. **Name collisions (Конфликт имен):** В коде вызывается метод `user.save()`. Анализатор видит имя `save`, но метод `save()` есть и в `models.py`, и в `models_order.py`. Компилятор берет **оба** файла в Tier 2\. Это немного увеличивает токены, но гарантирует, что контекст не потеряется.

### Как и для чего применить `@tool` в реальной разработке?

Декоратор `@tool` из библиотеки `langchain` превращает обычную функцию Python в **инструмент, доступный для автономных ИИ-агентов** (LangChain, LangGraph, CrewAI).

#### Как это работает в реальном проекте (Архитектура Coding Agent):

```
1. [Разработчик] ──► "Исправь ошибку списания денег в app/views.py"
                           │
                           ▼
2. [AI Agent (LLM)] ──► Видит доступный Tool: `get_compiled_code_context`
                           │
                           ▼
3. [Tool Call] ───────►get_compiled_code_context(target_file="app/views.py")
                           │
                           ▼
4. [Compiler] ────────► За 2 мс формирует промпт:
                        - views.py (FULL)
                        - models.py &amp; services.py (SKELETONS)
                           │
                           ▼
5. [AI Agent (LLM)] ──► Получает 300 токенов контекста и сразу пишет точный код.

```

#### Зачем это нужно?

Вам больше не нужно вручную копировать и вставлять 5 разных файлов в чат с ChatGPT/Claude, когда вы пишете код. Вы создаете агента (или CLI-утилиту), которому даете только путь к файлу, а агент **сам через этот tool собирает точный и минимальный контекст за 2 миллисекунды** и генерирует нужное решение.



#### Позволит ли укороченный промпт писать код через ИИ быстрее?

**ДА, и вот за счет чего:**

1. **Скорость генерации (Latency):** Модели ответа размышляют и генерируют отклики значительно быстрее, когда промпт сокращен на 70%.
2. **Экономия на API:** Вы передаете 3 000 токенов вместо 10 000+ токенов на каждый запрос.
3. **Отсутствие галлюцинаций в типах:** Модель видит сигнатуры и докстринги всех соседних классов (Tier 2), поэтому вызывает их функции с **правильными аргументами**, не отвлекаясь на их внутреннюю реализацию.



### О чем этот файл (`compiler.py` / заголовок в логе)?

Файл `compiler.py` — это **ядро и оркестратор** проекта `context-compiler`[2][3].

В выведенном логе показана первая строчка итоговой строки промпта (`prompt_text`), сгенерированной методом `to_prompt_string()`. Этот файл наглядно демонстрирует работу **3-уровневой стратегии контекста (3-Tier Strategy)**[1]:

* **Tier 1 (Full Source):** Полный исходный код файла, который сейчас редактируется (в данном случае сам `compiler.py`).
* **Tier 2 (Skeletonized Interface):** Файлы-зависимости в пределах заданной глубины `max_hops`. В них остаются только сигнатуры функций/классов, типы и докстринги, а тела функций заменяются на `...`[1].
* **Tier 3 (Total Exclusion):** Все остальные файлы репозитория, не связанные с задачей (они отбрасываются и занимают 0 токенов)[1].

### Что значит «обертка» (Wrapper)?

Термин **«обертка»** имеет два значения в зависимости от контекста:

1. **В коде (Технический смысл):** Это функция или класс, которые принимают существующий код и добавляют к нему удобный интерфейс или дополнительную логику.
  * *Пример:* В файле `my_agent_tool.py` вы обернули функцию `ContextCompiler` декоратором `@tool` из LangChain. Теперь обычный скрипт на Python превратился в официальный инструмент, который умеет вызывать AI-агент.
